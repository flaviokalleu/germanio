## Matriz

### Objetivo original
Linguagem de sistemas compilada, eficiente como C, expressiva como Python, com metaprogramação
forte. O compilador foi traduzido de uma versão de bootstrap em Pascal; `intern.md` avisa que o
código "is **not** a poster child of good Nim code".

### Filosofia
Sintaxe leve (indentação, pouca pontuação), poder no compilador (macros, templates, execução em
tempo de compilação) e liberdade de estilo para o programador. A regra de estilo do próprio manual
é a mais útil para o Germanio: "use the least powerful programming construct that remains
expressive" — proc, depois generic, depois template, só então macro (manual, seção Macros).

### Sintaxe
Indentação estrutural, `:` abrindo blocos (`if x:`), `=` abrindo corpos de rotinas, chamadas sem
parênteses (`echo x`), estilo de comando. Espaço também é significativo para operadores unários:
`echo $foo` difere de `echo ($foo)`, e `echo(1, 2)` passa dois argumentos enquanto `echo (1, 2)`
passa uma tupla (manual, Operators). Este último ponto é o preço de misturar "comando sem
parênteses" com expressões: o espaço vira sintaxe fora da indentação.

### Gramática
`doc/grammar.txt` é **gerada a partir de comentários no parser escrito à mão** (`compiler/parser.nim`:
"The parser strictly reflects the grammar ... In fact the grammar is generated from this file").
A gramática fica sempre em sincronia com o código, mas não é executável: é documentação extraída,
não uma especificação que gera o parser (o inverso do Python).

A indentação entra na gramática por pseudo-terminais (manual, Indentation):
- `IND{>}` recuo maior que o topo da pilha (e empilha), `IND{=}` recuo igual, `DED` desempilha;
- versões opcionais: `IND{>}?` aceita um token mais recuado **ou na mesma linha**; `optInd = COMMENT? IND{>}?`;
  `optPar = (IND{>} | IND{=})?`;
- exemplo do próprio manual: `stmt = IND{>} stmt ^+ IND{=} DED / simpleStmt`.

### Lexer/tokenizer
Só UTF-8; CR, LF e CRLF aceitos. "Indentation consists only of spaces; tabulators are not
allowed." O lexer **não emite INDENT/DEDENT**: "annotates the following token with the preceding
number of spaces; indentation is not a separate token. This trick allows parsing of Nim with only
1 token of lookahead." Um token que não é o primeiro da linha não carrega indentação. Comentários
`#` comuns nunca chegam ao parser; `##` (documentação) chega e tem posição gramatical (manual,
Indentation e Comments).

### Parser
Descendente recursivo à mão, com um algoritmo próprio para os 11 níveis de precedência. A
precedência de operadores definidos pelo usuário é deduzida do **primeiro caractere** do operador
(`*` → nível 9, `+` → 8, terminação `=` → atribuição, `->`/`=>` → o mais baixo) (manual,
Operators). A pilha de indentação vive no parser, consultada "at strategic places ... but
ignored otherwise".

### AST
Uma única árvore `PNode` (`ref TNode`) para tudo: literais, identificadores, símbolos,
instruções. `TNode` guarda `info: TLineInfo`, flags, um tipo opcional e, conforme o `kind`, um
valor ou `sons: seq[PNode]` (`compiler/astdef.nim`). `intern.md`: "The AST changes its shape after
semantic checking. This is needed to make life easier for the code generators." É a mesma árvore
que as macros recebem e devolvem (`std/macros`), o que torna o AST parte da API pública da
linguagem.

### Representações intermediárias
Em Nim 2, a própria `PNode` transformada serve de IR para os backends. Nimony (compilador rumo ao
Nim 3) troca isso por NIF, um formato textual de S-expressions em que a informação de linha é
parte do formato: "any tool that processes NIF automatically gets provenance for free", e os
arquivos NIF formam um "compiler database" indexado que ferramentas leem sob demanda
([Araq, S-Expressions](https://nim-lang.org/araq/sexpressions.html)). Nimony é trabalho em curso;
não tratar como resultado comprovado.

### Análise semântica
Separada do parse ("Semantic analysis is separated from parsing", `intern.md`), mas não em uma
passada única: numa chamada de macro, a semântica resolve a chamada, executa a macro, substitui a
AST e **reanalisa** a região, iterando se o resultado contiver outras macros (manual, Macros).

### Sistema de tipos
Estático, nominal para objetos, com generics, conceitos, distinct types e efeitos. Fora do foco
deste estudo.

### Type inference
Local (`let x = 1`); parâmetros e retornos de procs declarados. Não se aplica ao Germanio além do
princípio de inferir só o que é determinístico.

### Compiler/interpreter
Compila para C, C++, Objective-C e JavaScript; há uma VM para execução em tempo de compilação
(macros, `const`, `static`) e para NimScript. A portabilidade vem de gerar C: "porting the code
generator is not necessary" (`intern.md`).

### Runtime
Dois runtimes: o antigo (GCs refc, mark-and-sweep, Boehm) e o novo (ARC/ORC), ativo com
`nimV2` (`intern.md`); ORC é o padrão desde o Nim 2.0
([release notes](https://nim-lang.org/blog/2023/08/01/nim-v20-released.html)). Nimony propõe um
único modo (`atomicArc`) ([Nimony](https://nim-lang.org/araq/nimony.html)).

### Memory management
ARC/ORC (contagem de referências determinística + coletor de ciclos), destrutores e move
semantics. Não se aplica ao `.ge` de domínio.

### Standard library
Grande; no 2.0 vários módulos (conectores de banco, SMTP, FTP) saíram para pacotes Nimble
([release notes](https://nim-lang.org/blog/2023/08/01/nim-v20-released.html)).

### Package manager
Nimble (externo ao compilador, mas distribuído junto) e Atlas ("a simple package cloner tool")
([tools](https://nim-lang.org/docs/tools.html)). Dois gerenciadores convivendo.

### Formatter
`nimpretty` é distribuído ("format code according to the official style guide",
[tools](https://nim-lang.org/docs/tools.html)), mas a comunidade produziu o `nph`, "opinionated"
no estilo do Black, que compara a AST antes e depois e deixa o arquivo intacto se divergir, é
idempotente e evita alinhamento vertical para não gerar diffs
([nph](https://arnetheduck.github.io/nph/)). Um formatter oficial fraco convive com um de
terceiros forte: o mesmo resultado de não ter um formatter normativo.

### Linter
Não há linter oficial separado; o compilador tem `--styleCheck:off|hint|error` (conformidade com
NEP 1) e `--styleCheck:usages` ("only enforce consistent spellings of identifiers, do not enforce
the style on declarations") (`doc/advopt.txt`).

### Language server
`nimsuggest` é parte do core e responde consultas de editores (definição, sugestões)
([nimsuggest](https://nim-lang.org/docs/nimsuggest.html)). O `nimlangserver` é "based on
nimsuggest" e exige uma versão com `--v3`; existe uma alternativa (`nimlsp`) com nimsuggest
embutido ([langserver](https://github.com/nim-lang/langserver)). Uma camada LSP sobre um processo
de consulta do compilador, e não um segundo parser.

### IDE tooling
`nimgrep` existe em parte por causa da insensibilidade de estilo: "Nimgrep has particularly good
support for Nim's eccentric _style insensitivity_" (`--ignoreStyle`, `-y`)
([nimgrep](https://nim-lang.org/docs/nimgrep.html)). Ou seja, o `grep` comum deixou de bastar.

### Diagnostics
Mensagens com arquivo(linha, coluna); resolução de sobrecarga tem `--showAllMismatches` para
listar candidatos (`advopt.txt`). A qualidade das mensagens para iniciantes não foi avaliada nesta
passagem (não verificado).

### Testing
`testament`: runner com isolamento de processo, vários targets e relatório HTML
([tools](https://nim-lang.org/docs/tools.html)). A stdlib roda com `--styleCheck:usages` desde o
PR nim-lang/Nim#19715 (comentário de ringabout na RFC 456).

### Documentation
Manual (normativo de fato), `grammar.txt` gerado do parser, tutoriais, NEP 1 para estilo, `nim doc`
gerando HTML dos comentários `##`.

### Evolution process
RFCs como issues em `nim-lang/RFCs`, discussão aberta, decisão final do criador (Araq). A RFC 456
mostra o processo em funcionamento e seus limites (ver comparação abaixo): 268 comentários,
votação empatada (116 a favor, 121 contra) e fechamento pelo autor da linguagem porque nenhuma
release candidate do 2.0 mudou a regra.

### Backward compatibility
Mudanças grandes vêm em versões maiores (2.0: ORC padrão, `strictDefs`, remoção de módulos).
Nimony é um compilador novo, não uma evolução incremental do atual.

### Principais acertos
1. Indentação só com espaços, sem exceção.
2. Blocos por indentação numa linguagem compilada e de sistemas: a leveza visual não depende de
   ser interpretada.
3. Indentação na gramática por pseudo-terminais explícitos, inclusive o caso "mesma linha".
4. Continuação de linha decidida pela gramática (depois de operador, vírgula, parêntese aberto),
   sem `\`.
5. Gramática documental gerada do parser, portanto nunca desatualizada.
6. A regra "a construção menos poderosa que ainda expressa" como guia oficial.
7. Macros não mudam a sintaxe: "they cannot change Nim's syntax" (manual, Macros); todo DSL continua
   parseável pelo parser e pelas ferramentas comuns.
8. Linha de origem em cada nó (`TLineInfo`), e em Nimony a proveniência dentro do próprio formato.

### Principais problemas
1. **Insensibilidade de estilo**: exige ferramenta própria de busca, cria colisões em FFI (o caso
   Vulkan na RFC 456: `VkPipelineCacheHeaderVersionOne` e `VK_PIPELINE_CACHE_HEADER_VERSION_ONE`
   viram o mesmo identificador) e afasta usuários antes de experimentarem.
2. **Espaço significativo fora da indentação** (`echo (1, 2)` vs `echo(1, 2)`).
3. **Macros e templates não higiênicos por opção** (`inject`/`gensym`, `untyped`): o código de um
   projeto pode depender de nomes injetados por macros; ler um arquivo exige saber o que cada macro
   faz. É onde "cada projeto vira um dialeto" aparece: não na sintaxe (que é fixa), mas na
   semântica de blocos `untyped` que cada biblioteca interpreta à sua maneira.
4. **AST única mutável** que muda de forma depois da semântica: conveniente para codegen, frágil
   para ferramentas (nimsuggest precisa de campos extras, `endInfo` só `when defined(nimsuggest)`
   em `astdef.nim`). Nimony é em parte a resposta.
5. **Tooling duplicado**: nimpretty e nph, Nimble e Atlas, nimsuggest e dois LSPs.

### Complexidade acumulada
Dois runtimes, vários modos de memória, flags experimentais (`strictDefs`, `strictFuncs`), um
compilador de bootstrap herdado e agora um segundo compilador (Nimony). A sintaxe em si continua
pequena; a complexidade se acumulou na semântica e no tooling.

### O que Germanio pode aprender
Ver a comparação e a seção final.

### O que Germanio NÃO deve copiar
- Macros ou templates acessíveis no domínio: qualquer mecanismo de "o usuário define novas
  construções" fica no core, como capability, nunca no `.ge`.
- Precedência deduzida de caracteres, espaço que muda o parse de uma expressão, chamadas sem
  parênteses com semântica distinta de chamadas com parênteses.
- Liberdade de grafia sem verificação de consistência (o estado do Nim sem `--styleCheck:usages`).
- AST que muda de forma depois da semântica e é a mesma usada pelas ferramentas; o Germanio já
  separa `ast.Intent` (sintaxe com origem) de `ast.App` (modelo resolvido) e deve manter.
- Dois formatters ou dois gerenciadores de pacotes.

## Comparação com a sintaxe hierárquica do `.ge` (obrigatória)

Referência do Germanio: `docs/INTENCAO.md` › Layout e Gramática; `compiler/lexer/lexer.go`;
`compiler/parser/hierarquia.go` (`layoutTree`, `sections`, `sectionOf`); `compiler/parser/intencao.go`
(`foldWord`); `tooling/formatter`.

### 1. Onde a indentação vira estrutura

| | Nim | Germanio hoje |
|---|---|---|
| Lexer | anota em cada primeiro token da linha o número de espaços; sem token INDENT | emite `TokenIndent` com `Indent` no começo de cada linha não vazia (`lexer.go`) |
| Pilha | no parser, consultada em pontos estratégicos (`IND{>}`, `IND{=}`, `DED`) | no parser, em `layoutTree`: constrói uma árvore de linhas e depois reduz cada seção |
| Gramática | pseudo-terminais documentados em `grammar.txt` | EBNF do `INTENCAO.md` usa `ABRE`/`FECHA`, que nenhum componente emite como token |

Os dois fazem a mesma escolha (o lexer mede, o parser empilha), e ela é aceitável. A diferença é
que o Nim escreveu a regra na gramática gerada do parser. No Germanio, o EBNF fala de
`ABRE`/`FECHA`, mas o código fala de `TokenIndent` e de uma árvore de nós. A recomendação 1 de
`sintaxe-hierarquica.md` ("o lexer emite `BLOCO_ABRE/BLOCO_FECHA`") não foi seguida. Isso não é
um defeito, desde que o documento diga qual é a verdade. Escolha: ou `layoutTree` passa a ser
descrito como a definição de `ABRE`/`FECHA` (a opção do Nim), ou o lexer passa a emiti-los (a
opção do Python).

### 2. Tabulação

O Nim proíbe tabs sem exceção. O dialeto de aplicação do Germanio também proíbe (`lexer.go`,
erro "tab na indentação ... use espaços (4 por nível)"). Mas o núcleo estrito tem **outro**
caminho: o lexer em modo `NewGermanio` conta um tab como 2 espaços, e o parser estrito rejeita tab
num passo prévio com GE1002 "Use dois espaços por nível" (`compiler/parser/germanio.go`). Hoje o
usuário recebe duas instruções diferentes, 4 espaços e 2 espaços, conforme o front-end. A
contagem de tab como 2 no lexer é código morto perigoso: se o passo prévio for removido, a
largura do tab volta a decidir a estrutura em silêncio. Isso contradiz a nota do contexto de que
"o núcleo estrito já trata tab como erro": trata, mas no parser, e com outra unidade.

### 3. Continuação de linha

O Nim permite continuar uma expressão depois de um operador, de uma vírgula ou de um parêntese
aberto (`optInd` depois de cada operador em `grammar.txt`; "indentation within expressions is
allowed after operators, an open parenthesis and after commas", `tut1.md`). A continuação é da
gramática, não do lexer: a linha seguinte, mais recuada, é lida como parte da expressão porque a
regra aceita `IND{>}` naquele ponto. Custo: um recuo maior pode significar "bloco filho" ou
"continuação", e só a regra gramatical em curso desambigua.

O Germanio decidiu que "uma linha lógica não continua na linha seguinte" (`INTENCAO.md` › Layout).
Numa linguagem em que **recuo maior sempre quer dizer filho**, essa decisão é a certa e não deve
ser copiada do Nim: a ambiguidade "filho ou continuação" é exatamente o que um leigo não
conseguiria resolver olhando o texto. O Germanio substitui a continuação por estrutura: uma lista
longa vira um item por linha dentro da seção. Um ponto pendente: `sintaxe-hierarquica.md`
recomendava continuação implícita dentro de `( [ {` e de aspas triplas; o `INTENCAO.md` não
menciona isso, e o lexer tem texto multilinha. Convém declarar a exceção (só dentro de texto entre
aspas) no Layout normativo.

### 4. Insensibilidade de estilo de identificadores (foi um erro?)

**O que o Nim faz:** `a[0] == b[0]` e o resto é comparado sem maiúsculas/minúsculas e sem `_`; vale
também para palavras-chave (`notin` = `notIn` = `not_in`). Antes era totalmente insensível, e a
exceção da primeira letra foi introduzida para permitir `var foo: Foo` (manual, Identifier
equality). Os argumentos oficiais: bibliotecas com convenções diferentes não se chocam, o editor
pode exibir o estilo preferido, o programador não precisa lembrar a grafia exata.

**O que aconteceu:** a RFC 456 (2022-04-30, dom96) pediu a remoção no Nim 2. A motivação não era
bug, e sim adoção: "one of the main reasons that people do not even try Nim". Araq: "I don't care
much either way. I'm slightly in favor of removing it if we at the same time have the tooling
enforce nep1". Surgiu a alternativa `--styleCheck:usages` (exigir grafia consistente sem impor
estilo), a stdlib passou a usá-la, e a RFC foi fechada em 2023-05-21 sem mudança ("no release
candidate changes the style insensitivity rules"), com a votação dividida (116/121). Os custos
concretos citados: grep (resolvido com `nimgrep -y`, uma ferramenta a mais), colisões em wrappers
de C (Vulkan; a RFC 477 propõe crases sensíveis ao estilo como saída) e a percepção de risco em
equipes ([RFC 456](https://github.com/nim-lang/RFCs/issues/456)).

**Avaliação:** como *regra de igualdade*, não se mostrou fonte de bugs, e o Nim a manteve. Como
*regra de escrita*, foi um erro enquanto veio sem verificação de consistência: a solução que os
próprios mantenedores adotaram é "aceitar as variantes como iguais, mas exigir uma grafia só por
uso". O erro real foi estender a regra a um domínio em que nomes vêm de fora (FFI), onde a
igualdade do Nim cria colisões que o nome original não tinha.

**O Germanio já faz o mesmo, de forma mais forte.** `foldWord` (`intencao.go`) e `foldAccents`
(`lexer.go`) removem acentos. O nome de campo passa por `foldWord` (`declarativo.go`: `Name:
foldWord(name.Name())`), então `descrição` e `descricao` são o mesmo campo; as palavras das frases
e dos blocos passam por `wordsOf`, que também aplica `strings.ToLower` (`intencao.go`), então nomes
de dado e de seção ignoram acento **e** caixa. Nesse ponto é o regime totalmente insensível que o
Nim abandonou por causa de `foo: Foo`. Para o público
do Germanio a dobra de acento é justificável (teclados sem acento, digitação de leigos), e o
paralelo com o Nim diz o que falta:

1. **Consistência por uso.** Aceitar `descrição` e `descricao`, mas avisar quando o mesmo nome
   aparece com duas grafias no projeto, e fazer o `ge fmt` normalizar para a grafia da declaração.
   É o `--styleCheck:usages` do Nim, e responde ao problema de busca: com uma grafia só por
   projeto, o `grep` volta a funcionar sem um `nimgrep`.
2. **Colisões que a dobra cria.** A dobra junta `é` (verbo) e `e` (conjunção, que o parser usa como
   separador em `intencao.go`), `pôde`/`pode` (palavra de seção) e pares de domínio reais
   (`secretaria`/`secretária`, `cópia`/`copia`). Dois nomes que só diferem por acento devem ser
   erro de declaração com as duas origens (como o CUE faz com conflito), nunca a mesma coisa em
   silêncio.
3. **Nomes externos não se dobram.** O que vem de adaptadores (nomes de campos JSON, colunas,
   `integração nome "projects"`) já fica entre aspas e deve continuar literal: é a lição Vulkan e a
   proposta da RFC 477 (crase = literal).
4. **Tooling na mesma regra.** `gerar_gramatica.py` já gera regexes tolerantes a acento; a busca
   do `ge explain` e o futuro LSP precisam usar a mesma função de dobra, exportada do core, e não
   uma reimplementação.

### 5. Metaprogramação e o risco de dialeto

As macros do Nim não mudam a sintaxe, mas reinterpretam blocos `untyped` à vontade. O risco de
dialeto está no significado, não na forma. O Germanio já escolheu o oposto: as seções formam uma
tabela fechada (`sections` em `hierarquia.go`), e uma palavra fora da tabela é erro. A tentação
futura seria deixar integrações ou bibliotecas registrarem seções novas. Pelo exemplo do Nim, isso
deve continuar proibido no domínio. Uma capability nova entra no core, com nome e documentação, e
a regra "a construção menos poderosa que ainda expressa" vira a escada do Germanio: frase plana,
bloco, capability do core, adaptador.

### 6. Por que o Nim parece simples e o que disso vale para o `.ge`

A simplicidade visual do Nim vem de quatro decisões: indentação como bloco, pouca pontuação
obrigatória, uma só unidade de espaço (sem tabs) e comentários que não chegam ao parser. Três já
estão no `.ge`. A quarta (comentário invisível para o parser) o Germanio deve **não** seguir para
o formatter: o `ge fmt` precisa preservar comentários, e o Nim só resolve isso para `##`. O que
separa o `.ge` do Nim é a ausência de expressões na maior parte do domínio. Essa é a vantagem
estrutural: sem expressões, não há precedência, continuação nem espaço significativo dentro da
linha, e a gramática fica em "um item por linha sob uma seção".

Resposta curta à pergunta principal: o Nim fica visualmente simples por indentação estrita com
espaços, pouca pontuação e regras de layout escritas na gramática. Perde simplicidade quando o
espaço passa a significar coisas dentro da linha (operadores, chamadas) e quando a liberdade de
grafia vem sem consistência. O `.ge` já tem as partes boas e não tem expressões que exijam as
ruins. O que falta aprender vem do erro que o Nim corrigiu só com ferramentas: aceitar grafias
equivalentes exige verificar a consistência e tratar colisões como conflito.
